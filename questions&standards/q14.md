# Q14：管理层是否坦诚谈论困难

## Fisher 第 14 点

> Does the management talk freely to investors about its affairs when things are going well but “clam up” when troubles and disappointments occur?

本题判断：当公司确实遇到经营困难时，管理层是否在 earnings call 中主动、具体地承认并解释这些困难。

## 证据来源

使用两类工具：

1. `sql_query(query)`：识别公司是否出现可量化的经营困难；
2. `list_documents()` 和 `read_document(name)`：定位并阅读对应季度的 earnings call，检查管理层是否披露该困难。

不要只根据电话会的积极或消极语气判断，也不要只搜索负面关键词。必须先用数据库确认是否存在实际困难，再把该困难与对应季度的电话会进行核对。

## 时间范围和基准

按季度整理数据。对当前待判断季度，只使用它之前的五个完整季度作为基准：

```text
历史基准 = 前五个季度
当前季度 = 正在检查的季度
```

当前季度不得参与自己的均值和标准差计算。若不足五个完整历史季度，则不能使用异常值规则；应将该项标记为信息不足，或使用事先写明的保守处理。

标准差统一使用总体标准差，例如 Python 的 `statistics.pstdev()`。

## 困难指标一：经营现金流

### 计算

从 `quarterly_cash` 获取季度经营现金流 `operating_cash_flow`。同时从 `orders` 按季度汇总收入：

```text
quarterly_revenue = SUM(orders.amount)
ocf_margin = operating_cash_flow / quarterly_revenue
```

使用现金流率而不是现金流绝对金额，以减少公司规模变化造成的影响。

### 触发条件

若满足以下任一条件，则认为经营现金流出现重大困难：

1. 当前季度 `operating_cash_flow < 0`；
2. 当前季度现金流率同时满足：

   ```text
   current_ocf_margin < historical_mean - 2 * historical_std
   ```

   且：

   ```text
   historical_mean - current_ocf_margin >= 0.02
   ```

第二个条件表示当前现金流率不仅是历史异常低值，而且至少比历史均值低两个百分点。这样可以避免标准差很小时，极小变化被误判为重大困难。

## 困难指标二：退货率

### 计算

从 `returns` 按季度汇总：

```text
return_rate = SUM(units_returned) / SUM(units_shipped)
```

### 触发条件

对当前季度之前的五个季度计算退货率均值和总体标准差。只有同时满足以下条件，才认定退货率出现异常恶化：

```text
current_return_rate > historical_mean + 2 * historical_std
```

并且：

```text
current_return_rate - historical_mean >= 0.01
```

第二个条件要求退货率至少比历史均值高一个百分点，避免极小的统计波动被判定为经营困难。

这里的 0.01 是一个百分点。例如从 2% 上升到 3% 是上升一个百分点；从 2% 上升到 2.5% 是上升 0.5 个百分点。

## 其它可作为辅助证据的指标

如果数据明确支持，也可以检查：

- 订单金额或订单数量下降；
- `cash_end` 连续下降；
- 销售成本或销售管理费用显著上升。

这些指标用于帮助解释困难，不应在没有预先写明阈值的情况下临时加入主要判定规则。`capex_plan` 主要是未来计划，不能单独证明已经发生经营困难。

## 电话会核对标准

当至少一个困难指标触发时，阅读同一季度的 earnings call：

### PASS

管理层：

- 明确承认该问题或相关经营压力；
- 给出与数据库事实一致的具体说明；
- 最好说明原因、影响或应对措施。

### FAIL

数据库显示存在重大困难，但管理层：

- 完全没有提及该问题；
- 只使用笼统的正面表述来回避问题；或
- 给出与数据库事实明显不一致的说法。

### 没有困难

如果经营现金流和退货率均未触发困难条件，则不因这两个指标判定管理层隐瞒。此时 Q14 可判 `PASS`，但 summary 应说明“未检测到预先定义的重大困难”。

## 建议的结构化结果

让 agent 先输出结构化字段，再由程序决定最终 verdict：

```json
{
  "trouble_found": true,
  "trouble_types": ["ocf_margin", "return_rate"],
  "trouble_evidence": "当前季度现金流率低于前五季度均值两个标准差以上，且退货率超过历史阈值。",
  "management_acknowledged": false,
  "management_evidence": "电话会只讨论研发投入，没有承认现金流或退货率问题。",
  "assessment": "FAIL"
}
```

`assessment` 只能为：

- `PASS`：检测到困难且管理层充分披露；或未检测到预先定义的重大困难；
- `FAIL`：检测到困难，但管理层未披露、淡化或否认；
- `UNCLEAR`：数据不足、无法定位对应季度或电话会证据不足。

## 最终输出

结果应转换为作业要求的格式：

```json
{
  "points": {
    "14": "PASS"
  },
  "summary": "说明触发了哪些困难指标、历史基准和电话会中的披露情况。"
}
```

所有比率、均值、标准差和季度比较都必须由 SQL 或 Python 计算；agent 只负责解释文本证据和判断管理层是否真正回应了已检测到的困难。
